# Что изменилось в движке (ЛР1: Job System, база — ветка 3lab)

Коротко: взяла проект из ветки **`3lab`** (ECS, Assimp, текстуры, степлеры) и оставила всё, что в нём было. Поверх добавлено:
- сборка через **CMake + vcpkg**, так что проект собирается на любом компьютере, а не только у автора;
- исправлены найденные ошибки;
- **job system на enkiTS** (п. 2.1);
- задача №2: **параллельная подготовка отрисовки и анимации** на стресс-сцене из 20 000 кубов (п. 2.3);
- **Tracy** и **замеры до/после** (п. 2.4).

Базовые примитивы (треугольник, квадрат, куб) остались и работают.

> ⚠ **П. 2.2 (асинхронная загрузка ресурсов, L1) не сделан.** Менеджер ресурсов в `3lab` есть, но грузит всё синхронно. Всё нужное для 2.2 в job system уже есть, см. раздел 6.

**Куда класть в репозиторий:** это содержимое папки `Engine--3/Engine-main/` ветки `3lab`. Папку `glm/` в репозитории нужно удалить, glm теперь ставит vcpkg. Инструкция в корневом `README.md` («скопируйте путь к glm в свойства проекта») больше не нужна, актуальная лежит в `README.md` рядом с этим файлом.

## 3. Новое

### Job system — `Jobs/JobSystem.h/.cpp` (п. 2.1)
Подсистема движка поверх **enkiTS**: пул потоков, lock-free очереди, work stealing, приоритеты.
* `Initialize` / `Shutdown` в `Application`. Job system инициализируется **первой** и останавливается **первой**: живые задачи дорабатывают, новые не принимаются.
* Единая точка постановки задач:
  * `ParallelFor(count, minRange, fn)` — диапазоны на пуле, вызывающий поток тоже работает;
  * `Submit(fn, JobPriority, name)` → `JobHandle`, `Wait(handle)` — фоновые задачи;
  * `RunOnMainThread(fn)` + `PumpMainThread(лимит)` — очередь главного потока с лимитом на кадр (8).
* **Приоритеты:** ожидая `ParallelFor`, главный поток берёт только задачи High. Долгая Low-задача (загрузка) не выполнится внутри кадра.
* `--jobs=off` или клавиша **J** — всё выполняется на одном потоке. Это режим «до» в том же exe.
* Tracy: имена потоков `Job Worker N`, зоны ожидания `Wait for task` / `Idle`, графики `Jobs in flight`, `Main-thread queue`.

### Задача №2 (п. 2.3): что именно сделано

**Какая задача выбрана.** Кандидат из списка ТЗ «распараллеливание внутри одной системы». ТЗ описывает его так: «снапшот сущностей в массив → dispatch по диапазонам, работает и с хеш-таблицами, нужна сцена с тысячами сущностей, сделайте замерочную». Наш `World` хранит компоненты в `unordered_map`, так что это ровно тот случай.

**Что перенесено на job system.**

1. **Подготовка отрисовки** — `RenderSystem::Render` (`RenderSystem.cpp`):
   * снимок списка всех сущностей режется на куски по 256;
   * каждый кусок выполняется задачей job system: читает `Tag`, `Transform` и `MeshRenderer` из хеш-таблиц, считает мировую матрицу, проверяет, попадает ли объект в камеру (отбраковка по пирамиде видимости), и пишет готовый `DrawItem`;
   * главный поток склеивает куски по порядку (порядок отрисовки не меняется) и одним вызовом `DrawItems` записывает команды для GPU. Вид и проекция задаются один раз, а не на каждый объект.

   Раньше всё это делалось последовательно прямо в `Application::Draw`, по одному объекту за раз.

2. **Анимация стресс-сцены** — `UpdateStressAnimation`: кубы вращаются и покачиваются, и эта работа тоже раскладывается по потокам. Каждый куб пишет только свой `Transform`, поэтому блокировки не нужны.

Пока идёт подготовка, мир только читается: добавлять и удалять сущности в это время нельзя, поэтому потоки не мешают друг другу.

**«Замерочная» сцена.** Клавиша **B** или запуск с `--bench`: 20 000 кубов (`cube.obj`) с тремя текстурами, сетка под степлерами. Seed фиксированный, поэтому в каждом замере сцена одна и та же.

**Как показать «до/после».**
* Клавиша **J** на лету переключает job system: параллельно или на одном потоке. В заголовке окна видны FPS и число видимых объектов.
* Для замера: `Engine.exe --bench --jobs=off` или `--jobs=on`, либо сразу `bench.ps1`.

**Результат** (Release, 20 000 кубов, 3 + 3 прогона по 2000 кадров, подробно в разделе 5):

| | без job system | с ней | ускорение |
|---|---|---|---|
| подготовка отрисовки | 1.52 мс | 0.27 мс | ×5.6 |
| анимация | 0.59 мс | 0.14 мс | ×4.2 |
| кадр, медиана | 3.92 мс | 1.64 мс | ×2.4 |
| кадр, p99 | 8.42 мс | 4.24 мс | |

Зоны отмечены в Tracy (`RenderSystem::Prepare`, `StressAnimation`, `ParallelFor range`), поэтому на трейсе видно, как работа расходится по потокам `Job Worker N`.

**Что осталось команде.**
* **Согласовать выбор задачи в чате ММ** (так требует ТЗ). Например: «параллельная подготовка отрисовки и анимация в ECS на сцене из 20 000 сущностей».
* Для отчёта перемерить на свободном компьютере и **снять трейсы Tracy** «до» (J выключен) и «после» (J включён).

### Замеры (п. 2.4) — `Benchmark.h/.cpp`, `tools/bench.ps1`
`--bench`: фиксированная сцена и камера, прогрев, N кадров. Считаются медиана, p95 и p99 кадра и отдельно зон `StressAnimation`, `RenderPrepare`, `RenderRecord`; результат дописывается в CSV. `bench.ps1` запускает 3 прогона без job system и 3 с ней и строит сводную таблицу.

* В заголовке окна: состояние, режим job system, число видимых и всех объектов, FPS.

## 6. Для п. 2.2 (асинхронная загрузка) — что уже готово

```cpp
// чтение файла + разбор (Assimp / stb_image) - в фоне, низкий приоритет
jobs.Submit([=] {
    if (jobs.IsShuttingDown()) return;                         // корректный шатдаун
    auto mesh = MeshData::LoadFromFile(path);                   // CPU-работа в воркере
    jobs.RunOnMainThread([=] { d3d->UploadMeshToGPU(*mesh); }); // финализация на главном потоке
}, JobPriority::Low, "LoadMesh");
// Application::Update вызывает PumpMainThread(8) каждый кадр - это "памп с лимитом на кадр"
```
Placeholder тоже есть: если у меша ещё нет GPU-версии, `RenderSystem` рисует вместо него примитив «куб». Осталось:
- сделать `ResourceManager` потокобезопасным (мьютекс на кэш);
- перевести `InitScene` на фоновую загрузку;
- снять трейс «фриз до → ровный кадр после» (`--jobs=off` превращает `Submit` в синхронный вызов, это и есть «до»).
